绕过官方申请， 小米14Pro破解BL锁教程

candy2026-11-032026-11-03

一、先建立 4 个基础概念(后面每一步都依赖它们)

  1. 安卓开机的信任链

手机上电后,代码是一级一级加载、一级验证一级签名的:

PBL(芯片里固化的ROM,只读)
└─ XBL(高通次级引导,bootloader 第1级)
└─ ABL / UEFI(小米的 fastboot 界面就是它跑的)
└─ Linux 内核(boot.img 里的 kernel)
└─ init / Android 系统

两个关键机制就藏在这条链里:

  • BL 锁(Bootloader Lock / unlocked 标志)
    • 锁定时:fastboot flash 刷分区会被 ABL 拒绝;fastboot boot 临时启动外来镜像也会被拒绝。
    • 解锁时:这些操作才放行。解锁标志保存在设备的受保护存储里(TEE/FRP 区),正常只能通过小米官方解锁流程改写。
  • AVB(Android Verified Boot,安卓校验启动)
    • 系统每个分区(boot、system、vendor…)都有哈希/签名,这些”校验数据”集中放在一个叫 vbmeta 的分区里。
    • ABL 启动内核前按分区名 vbmeta_a / vbmeta_b 去找它,读出校验值,和实际分区比对。不一致就拒绝启动(或进入橙字警告状态)。
    • vbmeta 里还有一个 rollback index(回滚版本号),会和 TEE(安全世界,tz.mbn)里熔丝级的最低版本比较——版本号太低的旧系统不许启动,这就是”防回滚保护(anti-rollback)”。
  1. 这个工具在”撬”哪三把锁

┌──────────────────────┬──────────────────────────────────────┬──────────────────────────────────────────┐
│ 锁 │ 作用 │ 工具的对策 │
├──────────────────────┼──────────────────────────────────────┼──────────────────────────────────────────┤
│ Linux 内核权限 │ 普通 adb shell 没权限写底层分区 │ 用 GPU 驱动漏洞提权到 root │
├──────────────────────┼──────────────────────────────────────┼──────────────────────────────────────────┤
│ SELinux │ 即使 root,MAC 策略仍可能拦截写块设备 │ 把 SELinux 从 Enforcing 打成 Permissive │
├──────────────────────┼──────────────────────────────────────┼──────────────────────────────────────────┤
│ BL 锁 + AVB + 防回滚 │ 拒绝刷写/启动外来镜像、拒绝降级 │ 换掉 ABL + 改掉分区表 + 临时启动特制内核 │
└──────────────────────┴──────────────────────────────────────┴──────────────────────────────────────────┘

  1. 手机的两种”刷机通道”
  • adb:手机进了系统、开了 USB 调试后用。adb shell 是个普通权限 shell(u:r:shell:s0)。
  • fastboot(bootloader):在系统还没启动时由 ABL 提供。能不能刷,完全由 ABL 和 BL 锁状态决定。

脚本就是在这两个通道之间来回切。

  1. 这台设备是 A/B 分区结构

没有单独的 recovery 分区式老结构,关键分区都有两份:abl_a/abl_b、vbmeta_a/vbmeta_b。所以脚本里写什么都要刷两遍。设备名代号:小米14 = houji(后面线刷脚本会用它校验机型)。

二、整个工具的文件分工

Mi8g3-unlock-…/
├─ 8g3-unlock.bat ← 主控:状态机,整条攻击链都在这里(349行)
├─ toUnlock.bat ← 只是个”录屏/录日志”外壳
├─ check-unlock.bat ← 独立体检:看 BL 和工程 abl 还在不在
├─ adb-tool.bat ← 纯命令速查表,什么都不干
├─ adb.exe/fastboot.exe ← 谷歌官方 platform-tools
├─ 8650-Ennea.img ← 临时启动的特制内核(ANDROID! 格式,内部名 “lenine”)
└─ unlockFolder/
├─ bin/Xiaomi14/{exploit,su} ← 提权用(给一组机型共用)
├─ bin/Redmik80/{exploit,su} ← 另一组机型共用
├─ factoryImages/<机型>/
│ ├─ flash_all.bat ← 被改造过的官方线刷脚本
│ └─ images/
│ ├─ abl.elf ← ★工程版引导(关键)
│ ├─ gpt_both4.bin ← 原版分区表(用于事后复原)
│ ├─ xbl/tz/hyp/uefi… ← 整套旧版固件
│ └─ vbmeta.img(但刷它的命令被注释掉了)
└─ unlockGPT/<机型>/unlockgpt_both4.bin ← ★被篡改的分区表

注意 bin/ 只有两套:Xiaomi14 和 Redmik80。因为漏洞在 SoC(骁龙8G3=SM8650) 层面,同芯片的 7 款机型可以共用两套偏移配置。主控脚本菜单里那个 bin=
变量就是在选用哪一套(8g3-unlock.bat:48-89)。

三、逐行拆解主控 8g3-unlock.bat

我把 349 行分成 8 个阶段,你对照行号看。

阶段 0:界面与风险确认(1–118 行)

chcp 936 : 把控制台切成 GBK 中文编码
setlocal enabledelayedexpansion : 允许 !变量! 在循环/括号里实时取值
for /F %%a in (‘echo prompt $E ^| cmd’) do set “ESC=%%a”
最后这行是个经典技巧:cmd 默认拿不到 ESC(0x1B)字符,就起一个子 cmd 执行 prompt $E 把转义符”骗”出来,于是后面可以 %ESC%[31m 输出红色字。纯 UI,无实际动作。

  • 22–27:第一次风险确认,必须输 Y。
  • 29–91:机型菜单。每个选项设置 4 个变量,这是理解全脚本的钥匙:
    ┌───────────────┬────────────────────────────────────┐
    │ 变量 │ 含义 │
    ├───────────────┼────────────────────────────────────┤
    │ factoryImages │ 用哪个目录的线刷固件包 │
    ├───────────────┼────────────────────────────────────┤
    │ unlockGPT │ 用哪个目录的篡改 GPT │
    ├───────────────┼────────────────────────────────────┤
    │ bin │ 用哪一套 exploit/su(按 SoC 分两族) │
    ├───────────────┼────────────────────────────────────┤
    │ ifFlash=1 │ 是否需要跑线刷降级(全是 1) │
    └───────────────┴────────────────────────────────────┘

92 行先把工程 abl 的完整路径算出来,后面要显示给用户核对。

94–118:第二次最终警告,并把即将用到的 4 个文件路径打印出来。两次确认 + 显示路径,是这类高风险脚本的标准做法。

阶段 1:等 adb 设备上线(124–141 行)

:check_adb
adb devices | findstr /v /i “List” | findstr /i “device”
if %errorlevel% equ 0 goto flash_bin

  • findstr /v “List” 去掉标题行 List of devices attached;
  • 再找有没有状态为 device(已授权)的设备;
  • 每 2 秒一次,最多 10 次;失败就打印”开 USB 调试/装驱动”提示,等用户回车重来。

这个”检测→超时10次→提示人工→回车重入同一标签”的轮询模板,在脚本里出现了 5 次(adb 1 次、fastboot 3 次、SELinux 1 次),是它的核心容错套路。

▎ 学习点:批脚本里控制流全靠 :标签 + goto,errorlevel 是上一条命令的返回码,findstr 找到返回 0。

阶段 2:把提权程序推到手机(143–153 行)

adb push “…\bin%bin%\exploit” /data/local/tmp/exploit
adb push “…\bin%bin%\su” /data/local/tmp/su
为什么放 /data/local/tmp/?这是安卓上shell 用户唯一可写又可执行的目录(普通 App 私有目录不能 chmod 执行,外置存储又被挂成 noexec)。

(命令) || (失败处理) 是批脚本的异常捕获:推送失败就提示换线/重插,回车回到 :flash_bin 重推。

阶段 3:运行漏洞,获取 root(155–170 行)

adb shell chmod 755 /data/local/tmp/exploit /data/local/tmp/su
adb shell /data/local/tmp/exploit ← 第一次跑漏洞

for /f “delims=” %%i in (‘adb shell “/data/local/tmp/su -c ‘id’” 2^>^&1’) do (
echo %%i | findstr “uid=0(root)” && goto set_count_2
)
失败则回车 → 回到 :get_root 重来

注意它不盲目相信 exploit 打印的”成功”,而是用独立的 su -c id 验证输出里有没有 uid=0(root)。这是很正确的做法——漏洞成没成,用结果说话。

su 这个二进制我从符号表确认了,源码就是一个叫 su.c 的小程序(证据:二进制里有 su.c、setuid、setgid、execl、/system/bin/sh)。它的逻辑等价于:

// 据符号表还原的 su.c(教学用,非原样源码)
#include <unistd.h>
int main(int argc, char** argv){
if (argc > 2 && strcmp(argv[1], “-c”) == 0) {
setuid(0); setgid(0);
execv(“/system/bin/sh”, (char*[]){“sh”,”-c”,argv[2],0}); // su -c ‘命令’
}
setuid(0); setgid(0);
execl(“/system/bin/sh”,”sh”,0); // 交互 root shell
}

正常情况下普通进程调 setuid(0) 会被内核拒绝。它之所以能成功,是因为 exploit 已经在内核里打了补丁(下一节细讲)。

阶段 4:关闭 SELinux(172–199 行)

:set_count_2
set count_2=0
:selinux_permissive
adb shell /data/local/tmp/exploit ← 第二次跑同一个漏洞
…
adb shell “/data/local/tmp/su -c ‘getenforce’” | findstr /i “Permissive”
成功 → :flash_abl
10 次轮询不达标 → 重跑 exploit;重跑满 10 次仍 Enforcing
→ :exit 打印”严格模式,检查补丁日期!脚本退出。”

两个细节值得学:

  1. 同一个 exploit 要跑两次。从二进制字符串看,它每次执行会做两类内核内存改写:一类让 setuid(0) 放行(对应 setuid patch applied! Try getroot!),另一类把 SELinux 的强制开关清零(对应
    Wrote to %d locations. Check getenforce.)。第一次主要让 su 生效,第二次确保 enforcing 被关掉。
  2. “检查补丁日期”这句话暴露了前提:漏洞在新安全补丁上会被修复。脚本检测到 SELinux 还是 Enforcing,就判定内核补丁太新、提权没真正成功,直接放弃——因为下一步写 ABL
    必然失败,而且可能写到一半,风险极大。这是整条链最关键的安全闸。

到这里,手机系统内已经是 root + SELinux 放行状态。

阶段 5:换掉引导程序 ABL(201–213 行)

adb push “%abl_path%” /data/local/tmp/
adb shell /data/local/tmp/su dd if=/data/local/tmp/abl.elf of=/dev/\block/by-name/abl_a
adb shell /data/local/tmp/su dd if=/data/local/tmp/abl.elf of=/dev/\block/by-name/abl_b
adb reboot bootloader

逐点解释:

  • /dev/block/by-name/abl_a 是安卓按分区名建的软链接,指向 ABL 所在的真实块设备节点。直接 dd 裸写分区。
  • 脚本里写的是 /dev/\block,反斜杠是给 shell 转义用的,进到手机里就是 /dev/block。
  • 刷两个槽 abl_a、abl_b,防止设备从另一个槽启动把它覆盖回来。
  • 这个 abl.elf 是工程版(engineering)引导。正常小米 BL 锁定时,fastboot flash/boot 都会被生产版 ABL 拒绝;工程版 ABL 不校验锁状态,允许任意刷写和 fastboot boot。
  • 写完 adb reboot bootloader,手机重启进 fastboot——此刻运行的已经是工程 ABL 了,后面的违规操作才有可能。

▎ 这是全链”权限跃迁”最核心的一步:从”系统内 root”升级成”bootloader 层面不设防”。也解释了为什么阶段 4 必须确认 SELinux——否则 SELinux 会拦 root 写 /dev/block/* 设备节点。

阶段 6:等待 fastboot + 跑被改造的线刷包(215–261 行)

fastboot devices | findstr “.” ← 第2处设备轮询,确认进了 fastboot
if “%ifFlash%”==”1” goto run_flashall
:run_flashall
cmd /c “…\factoryImages%factoryImages%\flash_all.bat”

然后进入 flash_all.bat。这个文件非常重要,它不是原版小米脚本,被改过。以小米14(houji)为例,我把它解码出来,关键内容:

:: 0) 先校验机型必须是 houji,防止刷错变砖
fastboot getvar product | findstr “product: *houji” || exit /B 1

:: 1) 刷引导链/固件(全是旧版本,实现降级)
fastboot flash abl_ab images/abl.elf ← 又刷一次工程ABL
fastboot flash xbl_ab images/xbl_s.melf
fastboot flash tz_ab images/tz.mbn ← TrustZone/安全世界
fastboot flash hyp_ab images/hypvmperformance.mbn
fastboot flash uefi_ab images/uefi.elf
fastboot flash keymaster_ab images/keymint.mbn
… aop/cpucp/dsp/modem(注释掉) …

:: 2) 下面这几行被人故意注释掉了(双冒号):
::fastboot flash vbmeta_ab images/vbmeta.img ★不刷校验分区
::fastboot flash boot_ab images/boot.img ★不刷官方内核
::fastboot flash modem_ab images/NON-HLOS.bin ★不动基带
::fastboot flash super images/super.img ★不动系统大分区

:: 3) 收尾
fastboot flash userdata images/userdata.img ← 清空数据
fastboot set_active a
fastboot reboot bootloader

读出了三个设计者的意图:

  1. 降级安全补丁:把 xbl/tz/hyp/uefi 等整套固件刷成旧版本,让内核/GPU 漏洞可用、防回滚版本整体回到低位。super(system/vendor)没刷,说明数据系统可能保留/另装,但底层信任链全部回退。
  2. 故意不刷 vbmeta 和 boot:vbmeta 留空/不更新,为下一步”分区改名”和启动特制内核铺路;不刷官方 boot 是避免把启动链重新锁死。
  3. 自带机型校验 houji,防止用户给错机型刷固件——这是为数不多仍保留的官方保护。

为什么工程 ABL 已经 dd 进去了,线刷脚本还敢再 flash abl_ab?因为此时锁已经被工程 ABL 放开,fastboot 刷写畅通,顺便把两个槽的 ABL 再对齐一次。

阶段 7:篡改分区表 + 临时启动特制内核(263–268 行)

:flash_gpt
fastboot flash partition:4 “…\unlockGPT%unlockGPT%\unlockgpt_both4.bin”
fastboot boot “…\8650-Ennea.img”
echo [提示]请手动进入 Fastboot 回车开始检测
set /p “=”

(a) partition:4 刷的是 GPT 分区表

partition:4 是小米 fastboot 里指向磁盘 GPT 的特殊分区别名。我把 unlockgpt_both4.bin 和原版 gpt_both4.bin 做了逐字节比对,整个文件只差 59 个字节,用脚本解析 GPT
┌──────────────┬──────────┬────────────┬───────────────────────────────────────┐
│ 分区项 │ 原版名字 │ 篡改后名字 │ 其它字段(type GUID / 起止 LBA / 属性) │
├──────────────┼──────────┼────────────┼───────────────────────────────────────┤
│ 第 0x2700 项 │ vbmeta_a │ sbxiaomi │ 完全不变 │
├──────────────┼──────────┼────────────┼───────────────────────────────────────┤
│ 第 0x3580 项 │ vbmeta_b │ sbxiaomi │ 完全不变 │
└──────────────┴──────────┴────────────┴───────────────────────────────────────┘

它只改了名字,没动位置和大小。 为什么这一招致命:

  • ABL/AVB 是按名字找 vbmeta 的。vbmeta_a/b 消失后,校验链读不到校验数据;在工程 ABL(本就不强制)+ 即将启动的自定义内核下,启动时不会再用哈希拦 boot/system。
  • 防回滚比较依赖 vbmeta 里的 rollback index;vbmeta”找不到”,旧固件就不会被回滚保护拦下。这正是”高版本也能解”的关键。
  • 因为只改名不动数据,事后把原版 GPT 刷回来,分区内容立刻重新对得上,可逆,不会损坏用户数据分区。

both4 的含义:主 GPT + 备份 GPT 两份都改、按 4KB 扇区(UFS)布局(文件里 EFI PART 头在 0x1000 就是这个原因)。

(b) fastboot boot 8650-Ennea.img —— 临时启动,不刷入

我解析了镜像头:magic = ANDROID!,是标准安卓启动镜像;内核是 gzip 压缩的(在文件 0x1000),解压后约 4MB;镜像内部名 lenine(文件名 Ennea 是它的倒写变体);ramdisk 只有 372
字节,几乎是空的。

fastboot boot 和 flash 的区别:它把内核只加载到内存启动一次,不写进 boot 分区,重启即失效。这样即使内核有问题,正常分区也没被破坏。

这是整条链里最不透明的一环。 从脚本可观察到的事实是:启动过一次这个内核、再手动回到 fastboot 后,设备的 unlocked 标志变成了
true。内核镜像闭源,我们无法只从脚本确认它具体怎么改的标志(可能在内核内置初始化逻辑里通过某个驱动/安全分区写入解锁态)。

▎ 学习/风控双重要点:这种”一个来历不明的内核 boot 一下就解锁”的环节,从安全审计角度是最高风险点——你无法验证它除了解锁还写了什么。

阶段 8:复原分区表 → 判定结果 → 引导刷官方包(271–349 行)

用户手动回 fastboot 后:

:restore_gpt
fastboot flash partition:4 “…\factoryImages...\images\gpt_both4.bin” ← 原版GPT刷回

然后做两项体检:

fastboot oem device-info > temp_bl.txt
findstr /ic:”Device unlocked: true” → bl_status = 1 / 0

fastboot erase frp > temp_frp.txt
findstr /ic:”FAILED” → frp_success = 0 / 1

  • oem device-info 读 BL 锁状态;
  • erase frp 尝试擦 FRP(谷歌账号锁)。锁定/生产 ABL 下这操作会 FAILED;工程 ABL 下能成功,所以它被当成”工程 ABL 是否还在”的探针。

接着是全脚本设计得最好的部分——2×2 结局矩阵(318–337 行):
┌───────────┬────────────────────────┬───────────────────────────────────────────────────────────┐
│ BL已解锁? │ frp能擦?(工程ABL还在?) │ 含义与处置 │
├───────────┼────────────────────────┼───────────────────────────────────────────────────────────┤
│ 是 │ 是 │ 解锁成功 → 去刷官方固件 │

五、漏洞本体:exploit 到底干了什么(从二进制字符串还原)

我没有源码,但二进制里的调试字符串把算法讲得很清楚。以下机制是字符串直接证据,具体 CVE 编号我不确定,不杜撰:

证据字符串:/dev/kgsl-3d0、Can’t open
kgsl、kernel_pread_u64、kernel_pwrite_u64、walk_page_table、PGD/PMD/PTE、swapper_pg_dir、CHEESE_SWAPPER_PG_DIR_OFF、init_task_phys、__sys_setuid+0x40 BL
insn、sel_read_policy、setuid patch applied! Try getroot!、Wrote to %d locations. Check getenforce.。

这是一个典型的 Adreno KGSL GPU 驱动提权,步骤可还原为:

  1. 打开 GPU 设备节点 /dev/kgsl-3d0,通过特定 ioctl 在 GPU 显存和内核之间建立映射。这个驱动的漏洞让普通进程获得了对物理内存的任意读 / 任意写原语(kernel_pread_u64 /
    kernel_pwrite_u64)。
  2. 有了物理读写后,它需要把”内核虚拟地址”翻译成”物理地址”。办法是手动遍历内核页表:walk_page_table 沿 PGD→PMD→PTE 走一遍。为此先定位内核的顶级页表 swapper_pg_dir(用
    CHEESE_SWAPPER_PG_DIR_OFF 这类编译期偏移,找不到就 patchfinder 在内存里搜特征,字符串里的 efi_header_end、_text 就是找内核边界用的)。
  3. 定位 0 号进程 init_task(通过 init_task_phys),从而能顺着任务链表找到当前进程的凭证结构体 cred。
  4. 两处补丁:
  • 改 __sys_setuid 函数开头附近的一条 ARM64 分支指令(__sys_setuid+0x40 BL insn),让权限检查被跳过——于是 su 调 setuid(0) 直接成功;
  • 找到内核里 SELinux 的 enforcing 变量(字符串 sel_read_policy),把它写成 0——getenforce 于是变成 Permissive。
  1. 环境变量 CHEESE_SKIP_GPU、CHEESE_FORCE_MANUAL_PATCHFINDER、CHEESE_INIT_TASK_PHYS 等是给作者调试不同内核版本偏移用的开关。

一句话:GPU 驱动漏洞 → 物理内存读写 → 走页表定位内核数据 → 改 setuid 判定和 SELinux 开关。这是安卓内核提权非常经典的套路。

六、把整条链压缩成一张图

adb shell(普通权限)
│ push exploit/su
▼
KGSL 内核漏洞 ──► 物理内存读写 ──► 补丁 setuid + selinux_enforcing=0
│ (root + SELinux Permissive)
▼
dd 裸写 abl_a/abl_b = 工程版 ABL ──► reboot bootloader
│ (锁不再拦 fastboot)
▼
被改造的 flash_all.bat ──► 降级 xbl/tz/uefi 等旧固件(不刷 vbmeta/boot)
▼
刷篡改 GPT:vbmeta_a/b 改名 s bxiaomi ──► AVB 与防回滚失去依据
▼
fastboot boot 8650-Ennea.img(一次性内核) ──► 解锁标志被置位
▼
刷回原版 GPT ──► 探针验证(BL unlocked? frp 可擦?)──► 2×2 判定
▼
重刷官方线刷包,恢复干净系统

设计上有几个值得称道的工程思想(也是你以后分析别的工具的通用视角):

  • 每一步都做独立结果验证(id 查 uid、getenforce、device-info、erase frp),不信前置命令的自报成功。
  • 尽量可逆:内核用 boot 不 flash、GPT 只改名事后刷回、数据分区不动。
  • 危险操作前设闸:SELinux 没打成 Permissive 就绝不写 ABL。
  • 失败状态分类处置:2×2 矩阵明确区分”可重试 / 找作者 / 送售后”。

七、面向”安全加固”:每个环节该怎么堵

你说以后要做安全加固,那就把这条链当成一张攻击树,逐环给防御——防御的精髓是让链上任一环断掉。

  1. 对抗内核提权(最根本的一环)
  • 及时合入安全补丁,让 KGSL 漏洞失效(脚本自己都要检测”补丁日期”)。
  • 收窄 /dev/kgsl-3d0 的访问:用 SELinux neverallow 禁止 shell/untrusted 域访问 GPU 驱动的危险 ioctl;生产内核启用
    CFI、内核页表只读、CONFIG_DEBUG_RODATA、影子调用栈等,提高改内核代码/数据的难度。
  • 物理内存不可被 GPU 任意寻址:启用严格的 SMMU/IOMMU 隔离,缩小 ioctl 攻击面。
  1. 保护 ABL 不被替换
  • XBL 应当对 ABL 做签名链校验并熔丝到生产证书。这类攻击能成立,往往是因为工程/测试签名仍被设备信任——量产必须永久关闭工程证书信任。
  • 从系统侧,即便内核被 root,也应通过 UFS 写保护 / SMMU 让 HLOS 无法写 bootloader 分区(把关键引导分区排除在可写块设备外)。
  1. fastboot 安全
  • 生产 ABL 在锁定态必须无条件拒绝 flash partition(分区表)、flash bootloader 分区、boot、erase frp,且不接受工程命令。工程版 ABL 严禁外流。
  • GPT 写入要做一致性/白名单校验,禁止改受保护分区名。
  1. AVB / 防回滚
  • 校验必须 fail-closed:找不到 vbmeta 应当拒绝启动,而不是放行(本攻击依赖工程 ABL 把这个策略放松了)。
  • rollback index 由 TEE 熔丝强制,且与 vbmeta 是否可读解耦,避免”删掉 vbmeta 就绕过降级检查”。
  • 对 init_boot/vendor_boot 也做链式校验(脚本刻意不刷 boot/vbmeta,就是在躲这个)。
  1. FRP / 解锁标志
  • 解锁标志只能由 TEE 在鉴权(官方解锁服务器令牌)后改写,内核侧无任何接口能置位。
  • erase frp 在锁定态必须失败——它在此工具里还被当成工程 ABL 探针,说明这个命令本身就不该在生产引导里开放。
  1. 物理接触 + adb 的现实威胁
  • 整条链前提是”能进系统 + USB 调试已授权”。加固宣贯要告诉用户:不认识的电脑不要授权 USB 调试,锁屏密码要强壮,失窃后远程锁定。企业设备可通过 MDM 强制关闭 adb。
  1. 供应链审计视角
  • 工具里真正不可见的是四个闭源件:exploit、su、abl.elf、8650-Ennea.img。安全评估时,闭源引导/内核要在隔离环境抓它对持久化分区(modemst/persist/frp)的写入行为,确认没有后门/持久化
    。这也是普通用户最大的实际风险。

八、建议的进阶学习路线(由浅入深)

  1. 动手复现批脚本套路:在 Windows 上写一个 设备轮询 + errorlevel + findstr + goto 标签 的小脚本,理解它的状态机思维。
  2. 学安卓启动链与 A/B 分区:高通 PBL→XBL→ABL→kernel;/dev/block/by-name 软链接。
  3. 学 AVB:avbtool、vbmeta 结构、rollback index、dm-verity。
  4. 学 Linux 内核提权通用模型:页表(PGD/PMD/PTE)、cred 结构、commit_creds、SELinux enforcing 变量;再看一类公开的 KGSL ioctl 漏洞分析报告(原理层面)。
  5. 学 fastboot 协议与 GPT 结构:你已经亲手见过一份”改名两个分区项”的 GPT 差异,可以再用 gdisk 自己打印分区表对照。
  6. 防御侧:Android Compatibility Test 的 Verified Boot 要求、SELinux neverallow、Qualcomm secure boot / 熔丝文档。

实验闭环完成。主/备两份表头和表项的 CRC 全部一致。这一步虽然是练习,却挖出了一个我前面没讲透、但对”安全加固”极关键的点。下面带你读懂这份输出。

这个 GPT 文件在磁盘上的真实布局

CRC 全过,证明解析 100% 正确。文件 45056 字节,扇区大小是 4096(UFS),布局是:

文件偏移 内容
0x0000 (保留/MBR 兼容区)
0x1000 ←扇区1 主 GPT 表头(92字节)
0x2000 ←扇区2 主分区表项数组(96项 × 128字节 = 3个4K扇区)
0x6000 备份分区表项数组(和主表内容相同)
0xa000 备份 GPT 表头

关键分区(主表里的真实编号,和我上次按内存位置猜的 #14/#24 不同,这次以 CRC 校验通过的解析为准):

┌───────┬──────────┬────────────────┬───────┬───────┐
│ 表项# │ 名字 │ LBA 范围 │ 大小 │ 属性 │
├───────┼──────────┼────────────────┼───────┼───────┤
│ 8 │ abl_a │ 120326..122373 │ 8MB │ bit63 │
├───────┼──────────┼────────────────┼───────┼───────┤
│ 14 │ vbmeta_a │ 163558..163589 │ 128KB │ bit63 │
├───────┼──────────┼────────────────┼───────┼───────┤
│ 37 │ abl_b │ 363734..365781 │ 8MB │ bit63 │
├───────┼──────────┼────────────────┼───────┼───────┤

attr = 0x1000000000000000 是 bit63,即 GPT 规范的 “平台必备分区” 标志——vbmeta/abl 被标记为平台关键分区。

59 个差异字节到底是什么

逐字节定位后,差异干净地分成两组:

  1. 分区改名(主表 0x2738、0x35b8 + 备份表 0x6738、0x75b8,各 14 字节)
    把 UTF-16LE 的 vbmeta_a/vbmeta_b 改成 s bxiaomi。4 处 = 主表2条 + 备份表2条。type GUID、LBA、attr 一个字节没动。
  2. CRC 重算(主表头里 14 字节、备份表头也对应更新)
    • 表项 CRC:0x283a01e0 → 0xa51e50e8
    • 主表头 CRC:0x5ab88077 → 0x5e7ca6a2,备份表头 CRC 也跟着改。

我脚本里有几个”失败/0”是我自己取备份表基址取错造成的(备份表头里的 LBA 要用”距磁盘末尾扇区数”换算,不能直接乘扇区大小),用修正后的脚本复测——上面最后一步已经确认 6 项 CRC
全部一致。所以不是镜像坏了。

最有价值的加固教训(这个实验的真正目的)

注意这个事实:攻击者改完分区名后,把所有 CRC 都重新算对了,所以引导程序/fastboot 用”CRC 对不对”去检查分区表,会觉得这张表完全合法、欣然接受。

由此得到三条直接的防御结论:

  1. CRC/校验和只能防”意外损坏”,防不了”恶意篡改”——攻击者和你一样会算 CRC。要防篡改必须用密码学签名:由厂商私钥对分区表(或”受保护分区名清单”)签名,bootloader
    用烧录在熔丝里的公钥验签。改了名字就验不过。
  2. 分区名是安全锚点,就必须受保护。AVB 按名找 vbmeta 这个设计,默认”分区表不会被未授权修改”。一旦工程 ABL 放开了 flash partition:4 写 GPT 的口子,这个隐含假设就破了。加固方向是:
    • 锁定态 ABL 彻底禁止写 GPT(partition:4 这种命令在量产固件里不应存在);
    • 或在 bootloader 里对 vbmeta_a/b 等关键分区做按名字的白名单 + 存在性强校验,找不到 vbmeta 应当 fail-closed 拒绝启动,而不是放行。
  3. 工程/测试能力必须与量产设备物理隔离。整条链能成立的总开关,是那张允许任意刷写、允许写 GPT、允许 fastboot boot 的工程 ABL
    流到了用户手里。真正的根因加固在供应链:量产熔丝永久关闭对工程签名的信任,且让 HLOS(即使拿到内核 root)无法裸写 abl/GPT 所在分区(UFS 写保护 + IOMMU/SMMU 隔离)。

你亲手学会的可迁移技能

  • 用 magic + revision + headerSize 从文件里识别真假表头(同名串 EFI PART 会出现两次,要会区分);
  • GPT 头每个字段的偏移含义、GUID 的混合字节序、主备表的镜像关系;
  • 先信 CRC、再信解析结果的逆向方法论——任何结构解析,只要它自带校验,就用校验自证布局,避免”我以为”。

练习脚本在 /tmp/gpt_lab.py,你可以改它去解析电脑上任意一块盘的 GPT(macOS 下 diskutil list 找到磁盘后 sudo dd if=/dev/diskN of=gpt.bin bs=4096 count=12)。

index),让你亲眼看到”防回滚版本号”长什么样、TEE 是怎么拿它和熔丝比较的——这是上面第 2 条防御的另一半。需要的话我就带你做。
